# CLAUDE.md — project guide for Claude Code

## What this project is

A Node.js scraper that finds **Judaica retailers across Germany, England, France, Belgium, the United States (NY, NJ, FL so far) or Israel** on Google Maps for **Jaffa Glass** (Israeli maker of hand-crafted kosher glass Judaica with 24-karat gold paint). For each place, it reads the shop's website and **Impressum** to get an email address and a named contact. It scores how likely the place is to stock Judaica, then writes a spreadsheet and a mail-merge CSV with the partnership email rendered for each shop.

It is adapted from the archived *no-website lead scraper*, which found US businesses without websites. That project's browser handling (`browser.js`), in-page extractors (`dom-extract.js`) and HTTP transport (`http.js`) were kept, along with their tests. The US social-profile enrichment was replaced with website/Impressum contact extraction. The main difference in purpose: **here we want shops that do have a website**, because the website is where the email comes from.

Nothing costs money by default. Don't add a hard dependency on a paid service.

## Run

```bash
npm install
cp input.example.json input.json     # Windows: copy input.example.json input.json
npm run smoke                        # Berlin, 2 terms, 10 places, visible browser → output-smoke/
npm start                            # all of Germany → output/
npm run smoke:england                # London, 2 terms, 10 places → output-uk-smoke/
npm run england                      # all of England → output-uk/ (input.england.json)
npm run smoke:france / npm run france       # → output-fr-smoke/ / output-fr/   (input.france.json)
npm run smoke:belgium / npm run belgium     # → output-be-smoke/ / output-be/   (input.belgium.json)
npm run smoke:us / npm run us               # → output-us-smoke/ / output-us/   (input.us.json: NY, NJ, FL)
npm run smoke:israel / npm run israel       # → output-il-smoke/ / output-il/   (input.israel.json)
npm run smoke:sushi:israel / npm run sushi:israel   # sushi restaurants → output-il-sushi(-smoke)/ (input.israel-sushi.json)
npm run contacts -- --probe https://shop.de "Shop Name"
npm run contacts -- output/leads.json
npm run smoke:sushi:europe / npm run sushi:europe  # sushi, 46 European countries → output-eu-sushi(-smoke)/ (input.europe-sushi.json)
npm run sushi:germany                # the user's own 10 "Sushi <city>" searches → output-de-sushi/ (input.germany-sushi.json)
npm run smoke:art:us / npm run art:us  # US galleries, auction houses, dealers, advisors for Varnish AI → output-us-art(-smoke)/ (input.us-art.json)
npm run smoke:art:il / npm run art:il  # the same in Israel, Hebrew terms first → output-il-art(-smoke)/ (input.il-art.json)
npm run contacts -- output-us-art/leads.json --input input.us-art.json
npm test                             # 180 tests, offline; browser tests skip without Chrome
```

Use `--input path.json`, not `INPUT_FILE=`, because the env-var form fails silently in cmd.exe.

## Layout

```
src/
  main.js           orchestration: query loop, session hygiene, saving, summary
  config.js         COUNTRIES (DE, UK, FR, BE, US, IL): cities by region, districts, search terms, phone code, output dir; CAMPAIGNS (sushi, art); query matrix
  maps.js           one Maps query: consent → feed → detail pages → lead rows
  dom-extract.js    functions that run INSIDE the page (self-contained, serialised by puppeteer)
  relevance.js      Judaica keyword scoring → tier (a lead with campaign "sushi" goes to sushi.js, "art" to art.js)
  europe.js         EUROPE_MARKETS (gl, phone code, trunk prefixes, address names), cities and districts for the Europe sushi run
  sushi.js          the sushi campaign's scoring: Sushi place / Japanese / Asian restaurant / Other restaurant / Not a restaurant
  art.js            the art campaign's scoring (Gallery / Auction house / Art dealer / Art advisor / Not a buyer / Non-profit / museum), English and Hebrew, and its leads.json fields
  contacts.js       email extraction/ranking, Impressum name, greeting, link discovery, worker pool
  email-template.js loads templates/partnership-email.txt and fills {{placeholders}}
  output.js         dedupe, sort, xlsx (Outreach / No email found / All results), mail-merge.csv
  contacts-cli.js   re-run contact lookup on an export; --probe one site
  resume.js         continue a stopped run: load saved places, progress.json, --fresh backup
  whatsapp.js       WhatsApp evidence (site/listing links, mentions, mobile ranges), status, priority, wa.me chat link
templates/whatsapp-message.txt    the WhatsApp intro, prefilled in each chat link (never sent automatically)
  browser.js        local Chrome launch / optional Bright Data
  http.js           direct fetch with a browser fallback
templates/partnership-email.txt   the outreach email (first line "Subject: …")
templates/art-*-en.txt, art-*-he.txt  the art campaign's listing request (English; Hebrew for Israel)
test/               node:test + jsdom; fixtures/ has Maps markup and a fake German shop site
```

## Decisions that are load-bearing

- **One codebase, one profile per market** (`COUNTRIES` in `config.js`, chosen by `"country"` in the input file; default `DE`). A profile carries the Maps `gl`, the phone trunk code, the foreign-address filter, the search terms, the contact-page conventions (`contactKeyPage`/`contactPaths`: Impressum in Germany, Contact page in England) and a default output folder, so one market's run never overwrites another's. To add a market, add a profile and test it the way `test/england.test.js` does; don't branch on the country inside the code.

- **WhatsApp is evidence-based, never probed** (`whatsapp.js`). There is no free, permitted way to ask WhatsApp whether a number is registered, and automating WhatsApp Web to check breaks its terms and risks the user's account. So the status comes from what the shop publishes: a wa.me / api.whatsapp.com link or a number written next to "WhatsApp" on its site (`extractWhatsApp`, run inside the contact lookup) or on its Maps listing (`whatsappUrls` in `dom-extract.js`) gives **Yes** and the WhatsApp number itself; a bare mention or a mobile range gives **Likely**; a landline gives **Check**, because WhatsApp Business runs on landlines (21 of 34 hand-verified England shops were landlines). A `whatsapp_verified` value (yes/no) set by hand always wins. Every row gets a `wa.me/<n>?text=` link with `templates/whatsapp-message.txt` prefilled; the user presses Send. `prepareLeads` sorts the top two tiers by WhatsApp priority first, and the workbook leads with a **WhatsApp** sheet.
- **France and Belgium** reuse every rule above. Their legal notices are *mentions légales* (FR: *directeur de la publication*, *gérant*) and *colofon* (BE: *zaakvoerder*), so the role labels, honorifics (Madame/Mme/Monsieur, Mevrouw/Dhr.), company forms (SARL, SAS, BVBA, NV…), non-profit forms (ASBL/VZW, which always drop like e.V.), freemail (orange, free, skynet, telenet…) and public-body domains (`mairie-*.fr`, `<city>.fr/.be`, `*.gouv.fr`) are extended for them. Belgian postcodes have 4 digits; `cityFromAddress` reads 4–5.
- **The United States** (`US`, `US_CITIES` by state code) carries the state in every city name ("Lawrence, NY", "Borough Park, Brooklyn, NY"), because Maps would otherwise pick another state's town. The City and State columns come from the address (`addressTownWins`, `stateInAddress`; `cityFromAddress`/`stateFromAddress` read "…, Brooklyn, NY 11219"). Phones are +1; a bare ten-digit number gets the 1. +1 mobiles and landlines share area codes, so without evidence on the site or listing the WhatsApp status is **Check — US number** (`mobileUnknowable`), never "mobile" or "landline". *Temple …* / *Congregation …* / sisterhood / Hadassah names are institutions; *Temple* counts only at the start of a name, because the Rue du Temple is a Paris shopping street. `.gov` and `*.<state>.us` sites are public bodies. From the full NY/NJ/FL run: "Israel" as a person's name ("Barbara Israel Garden Antiques", "Israel Rose Jewelry") is not Israeli context (`personNamesOut`); "Jerusalem" alone is a place, not context, and a halal or Arabic-named market is not Jewish (US Arab groceries are often called Jerusalem); charity thrift shops (NCJW, Chabad, Hadassah) and "… at Temple X" gift shops are not buyers; a brand word ("Menorah") counts only for gift-like categories (`GIFT_LIKE`), on the listing and on the site; a Deli whose name says restaurant, diner or caterer is not a retailer. `isTarget` reads `relevance_tier`, so tests use `targetOf(lead)`. The US has its own email and WhatsApp templates (profile `emailTemplate`/`whatsappTemplate`; an input file's own `emailTemplate` wins): they say the collection is coming to the US, and the email carries the opt-out line CAN-SPAM requires.
- **Israel** (`IL`) searches in Hebrew first. Every Israeli shop is Jewish and kosher, so the profile sets `contextEverywhere`: Jewish/Israeli context words make no tier, and the outreach tiers (`includeTiers` on the profile, used when the input file has none) are **Judaica seller** plus **Glass & gift shop**, which in Israel also takes gift, souvenir and art shops (`GIFT_SHOP`). `scoreRelevance` reads the profile from `lead.country`. Hebrew Judaica words (`JUDAICA_HE`) and shop words (`RETAIL_HE`) match after up to two prefix letters (`countHits(…, { hebrew: true })`: ו, ה, ב, כ, ל, ש — not מ, because "מטלית" is a cleaning cloth and matched as טלית in the full run); "מנורה" is left out because it is any lamp. The gift tier is tight (`GIFT_SHOP` categories; a generic Store / Novelty Store only with a gift or Judaica name; any shop whose site names a Judaica object; never `NOT_GIFT`: toys, florists, photo, furniture, malls, promotional suppliers, glaziers) — the full run had Toys R Us, the LEGO Store and glass-railing installers. Israeli directories (Dapei Zahav `d.co.il`, B144, Easy, Zap) are platforms: 18 shops listed a d.co.il page and came back as 1800@d.co.il. The foreign filter drops ", Palestine" and abroad (a Bethlehem souvenir shop, a Milan arcade); Israeli towns in the West Bank carry no country in their Maps address and stay. Hebrew non-profits (`NON_PROFIT_HE`: בית כנסת, ישיבה, גמ"ח, עמותה, מוזיאון…) drop under any category unless the name has בע"מ. `cityFromAddress` drops Israel's 7-digit postcode. `CONTACT_LINK` knows צור קשר / אודות, `.co.il` / `.muni.il` are two-level domains, and `gov.il` / `muni.il` are public bodies. The email and WhatsApp templates are Hebrew (`templates/*-il.txt`, which may use `{{shop_name}}`). They are written as the one-time request to a business that Israel's anti-spam law allows: "פרסומת" in the subject, and an opt-out line.
- **Campaigns** (`CAMPAIGNS` in `config.js`, `"campaign": "sushi"` in the input file) point the scraper at another kind of buyer: `resolveCountry` merges the campaign's own regions, districts, search terms, `includeTiers`, templates, `outputDir` and `workbook` (`sushi-leads.xlsx`) over the market profile and sets `campaign`; `maps.js` copies it onto every lead, and `scoreRelevance` hands a lead with `campaign: 'sushi'` to `scoreSushi` (`sushi.js`). The feed's Judaica pre-screen (a restaurant is not a retailer) is replaced by the campaign's `dropAtFeed` tiers, and `progress.json` is keyed `IL-sushi`, so a sushi run never resumes a Judaica one. **Sushi** (Israel only, to sell glass plates and cups): sushi words (`סושי`, sashimi, nigiri, omakase…) match at a word start with Hebrew prefixes ("הסושיה"), but "maki"/"מאקי" only as whole words, because "making" starts with maki. Sushi in the name, category or description is a **Sushi place**; a Japanese/Asian kitchen (Japanese, Asian, ramen, poke, wok, Chinese, Thai… — in Israel most serve sushi) is **Japanese / Asian restaurant**, and moves up when its site mentions sushi; any other restaurant needs two sushi mentions on its site (a menu, not "salmon like in sushi"). Supermarket sushi counters, fish shops, supply stores ("Restaurant supply store" — the supply word beats the restaurant word), cooking schools and malls are **Not a restaurant** and are dropped at the feed. Ordering and booking sites (Wolt, 10bis, Mishloha, Ontopo, Tabit, rest.co.il, Uber Eats…) are platforms. The Hebrew templates (`templates/sushi-*-il.txt`) offer glass serving plates and cups, in the same one-time-request form as the Judaica ones. From the full sushi run: Asian words need a kitchen (a food category, an eatery name — restaurant, מסעדה, kitchen, בית אוכל, sushi bar — or no category), because Japanese spas, a Chinese-medicine clinic and Holon's Japanese Garden came back; an eatery name beats a shop category ("Sushi restaurant 🍣" filed as a Grocery Store); "Gastropub" and the Hebrew category "מסעדה" are restaurants. "Arad" alone is Arad, Romania (15 restaurants), so it is searched as "Arad, Israel" (`pickCity` drops ", Israel"); "Sushi Modi'in" found Sushi Modo in Canada; Hebron and Bethlehem addresses carry no country — all are in the IL `foreign` filter. Directory and delivery sites that leaked their own inbox are platforms (israelbusinessguide.com's gmail on 23 restaurants, Bali B Click, Valuecard, rol.co.il); Mishlohim pages are still read, because some show the restaurant's own address, but `PLATFORM_INBOX` discards Mishlohim's. Feed cards skip "No reviews" and address rows as categories, and a hotel blurb glued onto a category ("HotelSlick hostel with…") is cut.
- **Europe** (`EU`, `campaignOnly`: sushi only) is many countries in one run. `regions` are keyed by country code, and `scrapeQuery` merges `markets[query.state]` (`europe.js`) over the profile for each search: its Google `gl`, phone code and `trunks` (the national prefix to drop — none in Spain, Portugal, Luxembourg, Denmark…, Italy keeps its 0, "8" in Russia; a Luxembourg number once came back as +20221872). So use `"states"`, never a bare `"cities"` list, which has no country. The **Country** column (`country_name`, on every row in every market) is the market named at the end of the address abroad (`marketOfAddress`: a Strasbourg search finds Kehl, Germany), else the searched one. `cityFromAddress` reads the other European postcode styles ("1100-053 Lisboa", "00-950 Warszawa", "1012 LG Amsterdam", "111 51 Stockholm", "Athina 105 63", "Budapest, 1052", Eircodes) but never a house number; DE/BE/FR keep their old rule. `pickCity` turns "Ville-Haute Luxembourg" into a searched city. The campaign's `list` writes `sushi-europe-list.csv` (readable headers) and a first **Sushi restaurants** sheet; only **Sushi place** is a target. Sushi words include суши, суші, σούσι, 寿司. `"cities"` with exactly one `"states"` code puts the cities in that country (`input.germany-sushi.json`: the user's own "Sushi Berlin" … "Sushi Dortmund" list); `"workbook"`/`"listFile"` rename the outputs. Europe's DE market has `districtTowns` ("50823 Ehrenfeld" stays Köln). The English sushi email is the user's Email 1 (Zack, +972 53-854-8320); `{{first_name}}` is "there" unless filled in by hand — never guessed from an Impressum, where owners are often "Thi Bich Thuy Nguyen". Menu words (Speisekarte, Spezialitäten…) are not contact names. Maps' results list loads more only in a front tab with the browser not busy: website lookups running alongside the searches left "Sushi München" at 7, then 21 places (alone: 96), so `scrapeQuery` brings the Maps tab to the front, the session is refreshed every 60 places opened, and `"contacts": { "afterSearch": true }` (both sushi inputs) reads the websites only once every search is done; a resumed run does the same, the website lookup reads local numbers with each place's own `phone_code` (a German site's "0176…" once became +44 on the Europe run), and a run whose searches all finished but whose websites weren't all read (the container restarted mid-reading) reads them instead of exiting with "already finished".
- **Art campaign (Varnish AI)** (`"campaign": "art"`: `CAMPAIGNS.art.US` and `.IL`, which share `ART_CAMPAIGN`; scoring in `art.js`) builds a directory of art buyers for Varnish AI, a web app that helps people sell artwork. Varnish imports the run's `leads.json`, so its extra fields are a contract (below): change them only together with the importer. The places are the US art markets by state ("City, ST", as in `US_CITIES`) plus the gallery districts of the biggest (Chelsea, Tribeca, Wynwood, Canyon Road…), because Maps shows ~120 places per search; one term per kind of buyer runs everywhere first (`Art gallery`, `Auction house`, `Art dealer`, `Art advisor`). Tiers: **Gallery**, **Auction house**, **Art dealer**, **Art advisor** (the outreach tiers), **Not a buyer**, **Non-profit / museum**. Auction beats advisor beats dealer beats gallery; the name speaks first, then the Maps category, the description, and the site (where one "auction" is a charity gala, so it takes two). Framing beats "gallery" — many Maps "art galleries" are frame shops — unless the site shows exhibitions or represented artists; an artist's own studio needs represented artists (a CV lists exhibitions), a gift shop exhibitions. That verdict is `provisional` when the listing also says gallery, and the feed keeps "X Gallery & Framing" for its site to be read; it drops "Frame Masters" and the rest of **Not a buyer**: supply stores, paint-and-sip and classes, tattoo, printers, photographers, interiors, furniture, house and mural painters, conservators, and categories that have nothing to do with art (a "Car dealer" called Galleria Motors, cafés, malls). Museums, art centers, arts councils, public art, foundations and university galleries are dropped by `isSellable` (`artNonProfit`) for this campaign, because Maps files them as "Art gallery", a retail category; "Museum District", "Museum Hill" and "museum-quality" are not museums there (a Judaica run keeps its rule), and a commercial art school is Not a buyer, not a non-profit. The contract, on every art lead, from the listing until the website is read: `art_type` (`gallery` | `auction_house` | `dealer` | `art_advisor` | `""` for the last two tiers); `accepts_submissions` (`yes` | `no` | `unknown`: "we do not accept unsolicited submissions", "not currently accepting new artists", "unable to review portfolios", "submissions are closed", "by invitation only"… are no, and no wins over yes; "…via Instagram" is a rule, not a refusal; an auction house's "submit your artwork for an estimate" is a consignment); `submission_url` and `consign_url` (absolute; a link on a page read whose address or text says submissions / open call, or consign / sell / we buy / valuation; may be off-site, such as Submittable or a PDF; the submissions page is kept when it says no, since it states the policy); `accepts_consignments` (`yes` | `unknown`; a refusal is unknown); `specialties` (`; `-separated, lower case, from the fixed `SPECIALTIES` vocabulary; museum names and "installation photography by" don't count). The scorer gets the links from the contact lookup's `followLinks` (the campaign's two patterns): it keeps every matching link (`result.links` → `lead._siteLinks`, never written out) and also reads one submissions and one consign page on the site; other markets set none and read exactly what they did. `relevanceFields` spreads a scorer's `fields`; the workbook and leads.csv show the art columns after Category (`columns`). Gallery emails sit on /contact, /visit or /info (`contactPaths`). The templates (`templates/art-*-en.txt`) only ask a buyer whether it may be listed — Varnish users write their own messages to buyers — with the US opt-out line, and `[Your Name]` / `[Title]` / `[Postal address]` left for the user (CAN-SPAM wants the address). `SPECIALTIES` ends with *israeli art* and *judaica*: Varnish's own list (`lib/leads/labels.ts` there, same order) has them, and its forms and filters accept nothing else.
- **Art in Israel** (`CAMPAIGNS.art.IL`, `"country": "IL", "campaign": "art"`) keeps the IL profile's address, +972 and foreign rules (Bethlehem and Palestine drop). Terms are Hebrew then English, one per kind of buyer in each (`גלריה לאמנות` / `Art gallery`, `בית מכירות פומביות`, `סוחר אמנות`, `יועץ אמנות`); Tel Aviv-Yafo comes first with its gallery districts (Gordon Street, Florentin, Kiryat HaMelacha, Old Jaffa, Jaffa Port…), then Jerusalem (Hutzot Hayotzer, Musrara…), Haifa (Wadi Nisnas), the Sharon, the artists' villages (Ein Hod, Safed, Rosh Pina) and the south. The art word lists take Hebrew (`words(…, { he })`): after up to two prefix letters as in `countHits` ("הגלריה", "לאמנות"), with no end so plurals and construct forms match, and `HE_END` where the word must end ("סוחר", "דפוס"; "הדפס" is prints, "הדפסה" printing). Framing (מסגרות, מסגור, מסגרייה) beats גלריה under the English rules; studios (סטודיו, צילום), חנות יצירה, חומרי אמנות, חוגי/סדנת ציור, קעקועים, בית דפוס are not buyers; מוזיאון, בית האמנים, סדנאות האמנים, הגלריה העירונית, מרכז לאמנות, משכן לאמנות, מתנ"ס, עמותה, אגודת, ע"ר and university galleries are Non-profit / museum unless the name has בע"מ, and "…היא עמותה רשומה" on the site says so. Submissions: הגשת עבודות, קול קורא, "אמנים מוזמנים להגיש" are yes; "איננו מקבלים הגשות", "לא מקבלים פניות", "אין קבלת עבודות", "סגור להגשות", "בהזמנה בלבד" no — but "…בדואר, רק דרך הטופס" is a rule and "…עבודות למכירה" a consignment refusal, and work sent "להערכת שווי" is a consignment. Consignments: מסירה למכירה, קבלת יצירות למכירה, קנייה ומכירה של אמנות, "אנו קונים…", שמאות, הערכת שווי. Specialties stay English ("אמנות ישראלית עכשווית" → contemporary; israeli art); "צילום: X" and "צילום יוסי לוי" are credits, so Hebrew photography needs art context or another medium next to it, and "מוזיאון" plus up to four words is a museum name. The region column comes only from the address (`regionInAddress` → `regionFromAddress`), so it is empty in Israel: addresses name no district, and a Tel Aviv search finds Herzliya galleries. The Hebrew templates (`art-*-he.txt`) are the one-time request the anti-spam law allows: "פרסומת" at the start of the subject and of the WhatsApp text, "הסר" to opt out, `[כתובת למשלוח דואר]` left for the user. `runKey` (`resume.js`) keys `progress.json` `IL-art`.
- **One workbook layout, every run** (the user's "cleaned" file): WhatsApp · Outreach · No email found · All results, from `writeWorkbook`. A separate Summary-style copy was tried and removed: the user wants this layout every time. The WhatsApp sheet keeps one row per number (`uniqueByWhatsApp`: 21 Atza Sushi branches shared +972502975776), as Outreach keeps one per email. `fixMissingCode` repairs numbers sites write into WhatsApp links: the trunk 0 kept after the code ("+972 058…", "+49 0211…"), and no country code (nine digits or fewer always get the market's code; ten or eleven only when that makes one of its mobiles, so "wa.me/15730642210" on a German site is 01573…, not +1 573). All sushi runs, Israel included, use the user's JaffaGlass drafts (`templates/sushi-*-en.txt`). The IL profile also drops Ramallah/Al-Bireh and Jordan addresses and, via `foreignPhone`, +970 (Palestinian Authority) numbers on addresses that read "Jerusalem" or "Kiryat Arba".
- **A restart resumes; it never overwrites** (`resume.js`). Before this, re-running after a crash began at query 1 and its first save replaced the stopped run's files. Now `main.js` loads the output folder's `leads.json`, marks those places seen, re-queues the ones whose website lookup may not have finished (`contacts_checked` is set when a lookup completes), and starts at `progress.json`'s `next`. `progress.json` is written after every query and is trusted only if its country and query count match the current run. Without one, the run resumes at the last query that produced a place. A finished run exits with a hint instead of re-running; `--fresh` moves the old files to `previous-<date>/` first.
- **Maps is loaded with `?hl=en&gl=<country>`**: local results with an English UI. The extractors read English labels (`stars`, `reviews`, `Add website`). Supporting one UI language is much easier than supporting two. Don't drop `hl=en` without also teaching `dom-extract.js` German labels, and prove it with a fixture.
- **EU consent redirect.** From an EU IP, Maps first redirects to `consent.google.com`. `passConsent` answers it. `detectBlockPage` must **not** treat consent as a block (the US original did).
- **Phones are international.** `normPhone` in `dom-extract.js` turns a national `0…` number into `+<phoneCode>…` (`030 …` → `+4930…`, `020 …` → `+4420…`; `extractDetail` takes the code as its argument), keeps anything that already has `+`/`00`, and never rewrites a foreign number. A bare ten-digit number is American only in the US; elsewhere it is a national service number (Israel's 1-700 / 1-599 lines became "+1 1700…" in the sushi run), so it gets the market's code, and `whatsapp.js` marks Israel's `+9721[5-9]…` as **No — 1-700 / 1-800 service number**, with no chat link.
- **Foreign results are dropped** by address suffix (the profile's `foreign` regex). Border-city searches return Austrian, Swiss, French and Dutch shops.
- **Relevance matches at word starts only** (`countHits` in `relevance.js`). A bare substring test finds "tora" in "Restaurierung". Glass words match anywhere because of compounds like "Kunstglas" and "Bleiglas". A category in `NON_RETAIL_CATEGORY` (restaurant, café, cemetery, glazier…) caps the score unless the *name* carries a strong Judaica word.
- **Only sellable businesses are kept** (`isSellable` in `relevance.js`). A non-profit / religious Maps category (synagogue, community, non-profit, institute, school, library, museum…) or name (e.V., Gemeinde, Chabad, Stiftung, Verein…) drops the place at the feed stage and again on the detail page, before its website is read. A retail category (store, shop, gallery…) overrides a non-profit-sounding name, so a Chabad-run Judaica store survives. A Judaica word in the name overrides a wrong non-profit category ("Judaica Direct" filed as *Public Library*). Retail evidence for the tiers comes from the listing only, never the website, because every community site links to a shop page. A public body — website or email on a government domain (`stadt-*.de`, `*.rlp.de`) or on `<city>.de` — is dropped too, and this check runs before the Judaica-name exception ("Germania Judaica" is Cologne's city library). "Jewish / Israeli retail" needs Jewish/Israeli context in the listing, or a Judaica object named on the site; "Israel" in site text alone matched every bookshop and gallery with one Israeli author. Some names are institutions under any category (`INSTITUTION_NAME`: museum, synagogue, school, library, charity, foundation, e.V.): "Ben Uri Gallery and Museum" is filed as an *Art Gallery*. Chabad is deliberately not on that list, because Chabad runs real Judaica stores. `e.V.` always drops the place; the other institution words don't apply when the name is also a company or a bookshop (`COMMERCIAL_NAME`: GmbH, KG, Ltd, Buchhandlung, bookstore…), so "Deutsches Museum Shop GmbH", university bookstores and "Literaturhandlung im Jüdischen Museum" (a private Judaica bookshop) stay. The public-body check reads the website; the email decides only when there is no website, because a shop's pages can carry a city-portal address. `keepNonProfits: true` turns the filter off.
- **Brand-prone Judaica words** (`BRAND_PRONE`: menorah, star of david…) count in a business NAME only when the listing is a shop. England had "Menorah Massage", "Menorah Homes", "Menorah Hotel" and a landmark called The Menorah. Challah (bread) and kiddush (wine) are context words, not Judaica objects; the Judaica object is the *challah cover* or *kiddush cup*. "Jaffa" is not a context word (in England it's the orange and the cake).
- **City comes from the address** (`pickCity` / `cityFromAddress` in `maps.js`), not from the search, which is only where we looked: "Judaica Chelmsford" returned Manchester Judaica in Salford. In Germany, Maps' English UI puts the district after the postcode ("50823 Ehrenfeld", "01279 Dresden-Leuben"), so there the address town wins only when it is itself one of the searched cities (or its part before a hyphen is); otherwise the searched city stays. UK addresses carry the real post town. The address city also keys the duplicate check, so a place returned by searches in several towns is kept once.
- **One email per address**: `uniqueByEmail` keeps the best row per address on the Outreach sheet and in `mail-merge.csv`, so a chain (Shefa Mehadrin in Manchester and London) gets the email once.
- **Email ranking** (`rankEmails`): +40 for the site's own domain, +20 when the domain spells the business name, +25 when the local part does (`israelladen@mail.bgkorntal.de`), +15 for freemail, +10 for info/kontakt/shop prefixes, −30 for datenschutz/noreply/jobs, −25 for agency-looking domains. Web designers put their own address in the footer, and it must never win. The +40 applies only when the site is the shop's own (a homepage, or a domain spelling its name); a deep page on an umbrella organisation's site (`chabad-duesseldorf.de/…/aid/3860766` for Kosher King) gets none, so the umbrella's info@ doesn't win. Marketplace and platform pages (Kleinanzeigen, eBay, Etsy, AbeBooks, Facebook…) are never crawled, and their addresses are discarded. The crawl's base is where the Maps link lands after redirects (`1800eichlers.com` → `eichlers.com`), so contact links on the new domain are followed and emails rank against it; a redirect to a platform page is ignored. A site that gives no email and looks like a JavaScript app shell (`looksLikeAppShell`: under 400 characters of text on the homepage, or every address answering with the same page, as 1800eichlers.com does) is read again in Chrome (`http.fetchRendered`): the homepage and the contact links it draws. The run uses its own browser; `npm run contacts` starts a hidden Chrome with a throwaway profile only when a shell turns up, so it never clashes with a running scrape. `--probe` prints `pages_read`, every URL tried, where it redirected and whether it loaded. When the page Maps links gives no address (a branch page like `eichlers.com/pages/brooklyn`, a link with tracking codes, or a page that fails to load), the enricher tries the site's homepage, the contact page it links and the guessed contact paths, but only on the shop's own site (`ownWebsite`: a homepage, or a domain spelling the name), never an umbrella's. An address on an unrelated domain (`isThirdPartyEmail`: not the site's domain, not freemail, and neither its domain nor its local part spells the shop's name or site) is never the shop's email — `pickEmail` puts it under other emails: the web designer, app vendors (`gist-apps.com`), the kosher certifier whose page Maps linked (`ou.org`). Font-licence addresses (`*fonts.com`, `indiantypefoundry.com`), masked (`in**@…`) and placeholder (`you@isp.com`) addresses are junk. `repairTld` and `dropGlued` undo words glued onto addresses (`…@israelladen.deein`, `ninfo@…`).
- **Greeting gender only from evidence** (`greetingFor`): Frau/Herr, or a feminine title (Inhaberin, Geschäftsführerin, Direktorin…). `Mrs`/`Miss`/`Ms` give "Ms." and `Mr` gives "Mr." (an old `Mrs?` pattern once read Mr as female). Masculine titles are generic in German ("Inhaber: Irene Jaworski" produced "Dear Mr. Plattform"), so they never make it "Mr.". Otherwise use the full name. Never guess gender from a first name. With no name, `shortBusinessName` cuts the Maps SEO title at `|`, ` - ` or ` I ` and drops GmbH/GbR.
- **Impressum name extraction** stops at the first word that is a company form, an organisation compound (`…gemeinde`, `…handlung`, `…bibliothek`), a street (`…straße`, `…str`; `…ring`/`…damm` from the third word on), a digit, a word ending in a hyphen (`Online-`) or the next field label (`Sitz`, `Kontaktformular`, `Plattform`…). A company alone (`Vertreten durch: X GmbH`) yields no name, which is correct.

## Recipes

- **Add cities:** edit `GERMAN_CITIES` / `CITY_DISTRICTS` in `src/config.js`.
- **Add search terms:** `DEFAULT_CATEGORIES`. Put strong ones in `HIGH_YIELD` so they run across every city first.
- **Tune relevance:** edit the word lists in `src/relevance.js` and add a case to `test/pipeline.test.js`.
- **Tune the art campaign:** edit the word lists in `src/art.js` and add a case to `test/art.test.js` (Hebrew: `test/art-il.test.js`). Keep the leads.json fields and their values as they are unless the Varnish importer changes with them.
- **A Maps column goes blank:** save the page HTML into `test/fixtures/`, write a failing test in `test/dom-extract.test.js`, then fix the selector.
- **A shop's email is missed:** `npm run contacts -- --probe <url> "<name>"`. If the email is on a page that isn't linked, add the path to `guessContactUrls`. If it is obfuscated in a new way, extend `deobfuscate` and add a test.
